# Auto VPN: ответы на вопросы раздела 50 ТЗ

Ответы даны по состоянию реализации в этом форке. Там, где ответ не подтверждён измерением на устройстве, это написано явно.

| # | Вопрос | Ответ |
|---|---|---|
| 1 | Как определяем основное активное приложение? | `UsageStatsManager.queryEvents()` → `ACTIVITY_RESUMED`/`PAUSED`/`STOPPED`. `PrimaryForegroundAppResolver` отбрасывает System UI, клавиатуры, permission-диалоги, установщик, intent resolver и собственный пакет, требует стабильности кандидата 250 мс и переводит в `NO_ACTIVE_APP` только настоящую HOME-Activity (по компоненту и `priority ≥ 0`: у Settings есть служебная `FallbackHome`). Дополнительно ведётся набор всё ещё `RESUMED` Activity — он нужен для split-screen и для восстановления состояния при старте монитора |
| 2 | Какое разрешение требуется? | `android.permission.PACKAGE_USAGE_STATS`. Не runtime-разрешение: объявление в манифесте только добавляет приложение в системный список «Доступ к статистике использования», включает его пользователь |
| 3 | Можно ли обойтись без Accessibility? | Да. Accessibility не используется (AC-15). Цена — точность в split-screen ниже, чем у Accessibility |
| 4 | Реальная задержка определения? | Эмулятор API 37: от `am start` до решения 0,7–1,0 с (запуск Activity + до 500 мс опроса + 250 мс стабилизации). От решения до `VpnStartRequested`/`VpnStopRequested` — 0–10 мс. На физическом устройстве не измерялось |
| 5 | Как работает в Doze? | Монитор — foreground service, поэтому не попадает под ограничения фоновых сервисов, но при выключенном экране корутина приостановлена и опрос не идёт. Отложенный idle-таймер в Doze может сработать позже срока: это отложит отключение, но не включит VPN |
| 6 | Что на Samsung/Xiaomi/Huawei? | Разрешение и API стандартные, но OEM-менеджеры батареи могут убить foreground service. Xiaomi требует autostart, Huawei — «Run in background». `MainActivity.onResume()` и `BOOT_COMPLETED` восстанавливают монитор. **Не проверено на устройствах этих вендоров** |
| 7 | Focused app в split-screen? | Нельзя. Проверено на эмуляторе: касание другой панели меняет `mFocusedApp` в WindowManager, но `UsageEvents` не записывает ни одного события, обе Activity остаются `RESUMED`. Безопасное правило: видимое «Всегда отключать VPN» выключает туннель; иначе видимое «Через VPN» его удерживает; иначе решает последняя resumed-панель |
| 8 | Что делать с PiP? | PiP-окно находится в состоянии `PAUSED`, поэтому не входит в набор видимых и не удерживает VPN; банк во весь экран поверх PiP-плеера выключает туннель. PiP + launcher удерживает состояние до задержки отключения. **На эмуляторе не проверено:** в образе нет PiP-приложения |
| 9 | Как трактуем launcher? | `NO_ACTIVE_APP`: политика не применяется, запускается обычная задержка отключения (п. 18 ТЗ) |
| 10 | Как трактуем Recent Apps? | На большинстве прошивок Recents не даёт `ACTIVITY_RESUMED`, поэтому primary не меняется. Там, где Recents принадлежит launcher'у, поведение совпадает с launcher: задержка отключения, без немедленной смены политики |
| 11 | Как фильтруем System UI? | Префиксы `com.android.systemui`, `com.android.permissioncontroller`, `com.google.android.permissioncontroller`, `com.android.packageinstaller`, `com.google.android.packageinstaller`, `com.android.settings.intelligence`, `com.android.intentresolver` плюс список включённых IME из `InputMethodManager` и список home-приложений из `PackageManager` |
| 12 | Какой класс реально поднимает VPN? | `CoreVpnService`: `onStartCommand()` → `setupVpnService()` → `configureVpnService()` → `Builder.establish()`; Xray стартует в `CoreServiceManager.startCoreLoop()` |
| 13 | Как корректно остановить Xray? | Штатным путём `ServiceControl.stopService()` → `CoreVpnService.stopAllService(true)`: tun2socks, `CoreServiceManager.stopCoreLoop()`, `stopSelf()`, закрытие дескриптора. `AutoVpnCommandReceiver` вызывает именно его, а не «сырой» `stopService()`, когда ядро запущено |
| 14 | Когда TUN гарантированно уничтожен? | После `ParcelFileDescriptor.close()` в `stopAllService()`. На эмуляторе: `VpnStopped` (ядро остановлено) через 51–52 мс после команды, дескриптор закрыт ещё через ~100 мс (upstream делает паузу 100 мс перед `close()`) |
| 15 | Когда исчезает `TRANSPORT_VPN`? | На эмуляторе VPN-сеть переходит в `DISCONNECTED` в ConnectivityService через ~112 мс после решения об остановке, раньше закрытия дескриптора: сеть снимается, как только ядро перестаёт её обслуживать |
| 16 | Как предотвращаем race start/stop? | Один worker на conflated-канале в `VpnLifecycleController`: команды выполняются по одной, новая вытесняет ещё не начатую, каждая имеет generation. Покрыто JVM-тестами, включая серию из шести переключений |
| 17 | Можно ли предотвратить DIRECT leak во время STARTING? | Полностью — нет, без Always-on VPN с lockdown или root. Окно существует между `ACTIVITY_RESUMED` и `establish()`. Задокументировано как принципиальное ограничение |
| 18 | Что после reboot? | `BootReceiver` восстанавливает только монитор, туннель не поднимается. На эмуляторе монитор появился через ~13 с после `boot_completed` (доставка `BOOT_COMPLETED` последовательная); открытие Chrome → старт за 418 мс. Если к моменту старта монитора VPN-приложение уже открыто, оно находится по истории и туннель поднимается |
| 19 | Что при screen off? | По умолчанию выключенный экран = `NO_ACTIVE_APP`: на эмуляторе остановка через 10,05 с, после разблокировки при VPN-приложении наверху — старт за 159 мс. С опцией «Не отключать VPN при выключенном экране» туннель удержан (проверено 15 с) |
| 20 | Стоимость мониторинга по батарее? | Замер батареи не выполнялся (на эмуляторе нет её модели). Замер CPU-времени процесса `:daemon` на эмуляторе: 140 мс за 120 с при включённом экране (~0,12 % ядра), 0 мс за 120 с при выключенном |
| 21 | Стоимость частых запусков Xray? | На эмуляторе с локальным SOCKS-профилем старт 106–636 мс, стоп 51–52 мс; 13 циклов за 18 с прошли без ошибок. TLS и удалённый сервер в замер не входили. Частота смягчается задержкой отключения и стабилизацией кандидата |
| 22 | Нужно ли менять Xray core? | Нет. Весь жизненный цикл — на стороне Android |
| 23 | Что ещё русифицировать в upstream? | Русская локализация upstream уже большая; новые 35 ключей переведены полностью. Отдельный аудит существующих экранов не проводился |
| 24 | Что принципиально нерешаемо без root/system? | Focused pane в split-screen (подтверждено экспериментом); атомарное отсутствие утечки в окне `STARTING`; мгновенный разрыв уже установленных TCP/QUIC-сессий и сброс DNS-кеша чужого приложения; защита от OEM-менеджера батареи, убивающего foreground service |
